issue-599-why-detection-at-post-processing
Can also be done at pre-processing phrease by searching required keywords in the raw text, but
the complexity of doing that is almost equal create another parser, which duplicate the next
phrase (PyParsing).
Can not be done in PyParsing phrase becuase during parsing the function is going to get deferred,
so we cannot take a look inside it and analye unreachable code.
The only choice left is at post-processing phrase.

issue-599-detection-algorithm-explain
issue-599-detection-algorithm-more-examples
The detection algorithm only detect unreachable code at the first level (First indentation). The unreachable statements are
return, break, continue, and raise. The function have 3 guard clauses following with "the gate" (the main unreachable code analysis logic).
The guard clauses are existed to allow only line with specific conditions (e.g level 1 only) to be analyzed.
This mean if the any of the guard clauses is true then it will skip the whole code block (def, for, while, try, with).
Notably, we only analyze only functions' direct body because going for more than that would be too complex.
The error is report at terminator line not the unreachable line.
The function is going to analyzed functions within a file one by one until there is no function left.


issue-599-performance-analysis
The performance impact of detect_unreachable_code is negligible. It adds one lightweight linear pass per function body,
using the same pattern as detect_is_gen and transform_returns which already exist. Per-line cost is string splitting,
integer comparisons, and precompiled regex matching — cheaper than transform_returns which also calls PyParsing parsers per line.
The real bottleneck is the PyParsing phase, which is orders of magnitude more expensive than any post-processing line iteration.
The detection always runs regardless of --strict mode, but the total added cost is under 0.1% of compilation time.

issue-599-more-test-case-impl-plan
11 new test methods to add inside TestCompilation in main_test.py at line 1118.
2 positive tests verify the detector catches unreachable code after raise statements (with and without arguments).
9 negative tests verify no false positives for suppressed patterns: nested def, for loop, while loop, try block,
with block, if without else, if/else all-return, return-only function, and empty function.
Positive tests use --strict with expect_retcode=1; negative tests use --strict with expect_retcode=0 so any false positive becomes a hard failure.
Goal is both correctness verification and executable documentation of the detection scope for contributors.
