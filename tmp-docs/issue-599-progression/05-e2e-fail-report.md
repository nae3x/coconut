# Issue 599: End-to-End Test Failure Report

## Summary

Running `make test-univ` fails during compilation of `target_sys_test.coco` with `--strict` mode. The unreachable code checker (implemented for issue 599) produces false positives on two patterns found in the test file.

---

## Failure 1: `it_ret` and similar functions (user-written pattern)

### What fails

Three functions in `coconut/tests/src/cocotest/target_sys/target_sys_test.coco` use the pattern `return` followed by `yield` to create generator functions:

```coconut
def it_ret(x):        # line 23
    return x
    yield None

def it_ret_none():    # line 34
    return
    yield None

def it_ret_tuple(x, y):  # line 38
    return x, y
    yield None
```

This is a well-known Python idiom. The `yield` statement (even though unreachable) makes Python treat the function as a generator. In a generator, `return x` raises `StopIteration` with `value=x` instead of returning normally. The tests at lines 179-196 verify this behavior.

### Why it fails

The unreachable code checker in `detect_unreachable_code` sees `return x` at the top level of the function body, records it as a terminator, then sees `yield None` as code after the terminator — and reports it as unreachable.

The checker is technically correct: `yield None` is unreachable. But this is an intentional, idiomatic pattern.

### How to fix

Rewrite the test functions to use `if False: yield None` before the `return` instead of `yield None` after it:

```coconut
def it_ret(x):
    if False:
        yield None
    return x
```

This preserves the generator semantics (the function still contains `yield`, so Python treats it as a generator) without triggering the unreachable code check. The same change applies to `it_ret_none` and `it_ret_tuple`.

## Failure 2: `yield def` inside `target_sys_test` (compiler-generated pattern)

### What fails

After fixing the three functions above, compilation fails again at:

```
CoconutStyleError: found unreachable code after return statement (line 201 in 'target_sys_test.coco')
  yield def f(x) = x
```

The code at lines 201-207:

```coconut
yield def f(x) = x
l = []
yield def g(x):
    result = yield from f(x)
    l.append(result)
assert g(10) |> list == []
assert l == [10]
```

This tests Coconut's `yield def` feature, which defines a function that is implicitly a generator.

### Why it fails

This requires understanding how `yield def f(x) = x` is compiled and how the checker analyzes it.

#### Step 1: Parsing and `keyword_funcdef_handle`

When Coconut parses `yield def f(x) = x`, the `= x` math-def syntax compiles the body to `return x`. Then `keyword_funcdef_handle` (compiler.py:5316-5333) processes the `yield` keyword by **appending** an `if False: yield` block to the end of the function body:

```python
def keyword_funcdef_handle(self, tokens):
    keywords, funcdef = tokens
    for kwd in keywords:
        if kwd == "yield":
            funcdef += handle_indentation("""
if False:
    yield
            """, add_newline=True, extra_indent=1)
    return funcdef
```

After this step, `f`'s body (in compiled form with indent markers) is:

```
return x
if False:
    yield
```

The `if False: yield` makes `f` a generator (Python sees `yield` in the function body).

#### Step 2: `proc_funcdef` calls `detect_unreachable_code`

When `proc_funcdef` (compiler.py:2810) processes `f`, it calls `detect_unreachable_code` on the raw body lines at line 2926 — **before** `transform_returns` runs. At this point the body still contains `return x` (not yet transformed to `raise StopIteration`).

#### Step 3: The checker traces through the body

The checker iterates over the normalized lines of `f`'s body. Here is the actual trace (verified by monkey-patching):

```
raw_lines:
  0: '⁋return x‡1⏹\n'          (return x with line comment)
  1: '‡2⏹\n'                    (blank line with line comment)
  2: '¶⁋if False:\n'            (dedent then indent: same level)
  3: '⁋    yield\n'             (indented yield)
  4: '¶¶'                       (two dedents)

After normalize_indent_markers:
  level=1  base='return x'   → matches terminator_stmt_regex → last_terminator = ("return", line_1)
  level=1  base=''           → blank, skipped
  level=1  base='if False:'  → active, last_terminator is set → ERROR: unreachable code after return!
  level=2  base='yield'      → level != 1, skipped
  level=0  base=''           → level != 1, skipped
```

The checker correctly identifies that `if False:` at level 1 comes after `return x` at level 1. But the `if False: yield` was **generated by the compiler itself** in `keyword_funcdef_handle` — the user never wrote unreachable code.

### Root cause

`keyword_funcdef_handle` **appends** `if False: yield` to the **end** of the function body. When the body already ends with a terminator (`return x`), this creates unreachable code that the checker flags as an error.

### How to fix

Change `keyword_funcdef_handle` to **prepend** the `if False: yield` block at the **start** of the function body instead of appending it at the end.

Currently (compiler.py:5320-5328):

```python
if kwd == "yield":
    funcdef += handle_indentation("""
if False:
    yield
    """, add_newline=True, extra_indent=1)
```

The fix: find the first `openindent` marker in `funcdef` (which marks the start of the function body) and insert the `if False: yield` block right after it. With `extra_indent=0` since the insertion point is already inside the body's indent level:

```python
if kwd == "yield":
    if_false_yield = handle_indentation("""
if False:
    yield
    """, add_newline=True)
    # Insert at the start of the function body (after first openindent)
    idx = funcdef.index(openindent) + 1
    funcdef = funcdef[:idx] + if_false_yield + funcdef[idx:]
```

After this change, `f`'s body becomes:

```
if False:
    yield
return x
```

The checker would then see:

```
  level=1  base='if False:'  → no last_terminator set, normal code (resets last_terminator to None)
  level=2  base='yield'      → level != 1, skipped
  level=1  base='return x'   → matches terminator, sets last_terminator
  (end of body)              → no code after terminator, no error
```

No false positive. The function is still a generator (Python checks for `yield` anywhere in the function, not its position).
